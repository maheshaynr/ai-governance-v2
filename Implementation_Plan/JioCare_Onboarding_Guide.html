🛡️ Guardrail · Agent Governance

Re-registering JioCare Helper

JioCare's device-diagnosis assistant was integrated with the platform about a week ago and worked end to end. Since then, Guardrail's Agent Governance layer was built out (the same model VOXA's skills now run on), and JioCare was never carried over into it. This guide covers exactly what's missing and how to close the gap.

Current state, checked directly against both databases: JioCare has no registered agent identity in Guardrail (agents table has zero rows for it), no IAM entitlement, and — as of this session's data cleanup — no active DPDP consent either. A DPDP notice for it still exists (jio-device-diagnosis-notice-v1), and historical decision records confirm the purpose and wiring worked before, but every live grant tied to it is gone.

01 The three layers, applied to JioCare

Every agent on this platform is governed by three independent checks, in this order. A gap in any one of them blocks the flow — that's what's currently happening to JioCare.

Layer 1 — Identity

Agent Registry

Who is this caller? Established once via /v1/agent/register, which returns an agent_id and a secret.

Missing
Layer 2 — Authorization

IAM Entitlement

Is this specific agent allowed to act, for this principal, within this app? A (principal, agent, app) grant.

Missing — and unmapped
Layer 3 — Consent

DPDP Consent

Has the Data Principal agreed their data can be used for this purpose? Checked against a live consent record.

Notice exists, consent doesn't

These are deliberately separate from each other — see Agent_Governance_Layer_Design.md for the full rationale. A principal saying yes to a purpose (Layer 3) never implies the agent asking is authorized to ask (Layer 2); each has to be independently true.

02 What Guardrail does (nothing from JioCare needed)

A

Map JioCare's purpose to an "app" for IAM

Today, _purpose_to_app() only recognizes swiggy, teams, kite, and yahoo — an unrecognized purpose skips the IAM gate entirely rather than failing closed on it. JioCare's purpose, device_diagnosis_ai_analysis, isn't in that list, so it currently bypasses authorization checking altogether. Bringing JioCare to parity with VOXA means adding a mapping:

_PURPOSE_APP_SUBSTRINGS = (
    ("swiggy", "swiggy"),
    ("teams", "teams"),
    ("kite", "kite"),
    ("yahoo", "yahoo_finance"),
    ("device_diagnosis", "jiocare"),
)

Without this, JioCare traffic is never IAM-gated — every call falls straight through to the consent check.

B

Grant the entitlement, once JioCare's agent_id exists

A one-time call after step 1 below completes:

governance_db.grant_entitlement(
    principal_ref="<real subscriber id>",
    agent_id="<jiocare agent_id from registration>",
    allowed_app="jiocare",
)
C

Re-issue DPDP consent per real subscriber

The notice already exists — no new notice needed:

notice_ref: jio-device-diagnosis-notice-v1
purpose:    device_diagnosis_ai_analysis
owner:      ai-jiocare-helper

What's missing is the consent record itself (DPDP Engine → Consents → Grant), one per real subscriber, referencing that notice.

03 What JioCare implements

1

Register the agent — once, ever

Call POST /v1/agent/register. Store the returned secret; it's shown exactly once.

POST /v1/agent/register
{
  "agent_name": "JioCare Device Diagnosis Helper",
  "business_unit": "JioCare",
  "owner_name": "<team/owner>",
  "location_of_deployment": "<prod/staging>",
  "in_house_or_external": "in_house",
  "device_id": ""
}

→ 200
{
  "agent_id": "jiocare-device-482913",
  "agent_secret": "<shown once — persist this>",
  "identity_assignment_timestamp": "…"
}
2

Send identity on every call

Every request from here on carries these two headers — this is the part that's currently missing entirely (today's calls go through unauthenticated, so nothing is logged against JioCare at all):

X-Agent-Id: jiocare-device-482913
Authorization: Bearer <agent_secret>
3

Gate the diagnosis action through the decision check

Before pulling any device/modem/STB data for a customer, ask Guardrail whether this is authorized:

POST /v1/agent/decisions/check
{
  "principal_ref": "<real subscriber id>",
  "purpose": "device_diagnosis_ai_analysis",
  "operation": "ANALYZE_DEVICE_LOGS",
  "data_categories": ["DEVICE_MEDIA"],
  "device_id": ""
}

A DENY with reason_code: IAM_SCOPE_EXCEEDED means step B above hasn't run yet for this subscriber. A DENY with a DPDP reason means step C hasn't.

4

Run the customer's message through content validation

Anything the customer types, and anything the AI is about to send back, goes through /guardrail_validate — this is what catches an account number or OTP the customer pastes into the chat before it's masked or flagged.

POST /guardrail_validate
{ "text": "<message>" }

→ { "flag": "AI Guardrail flag: PARTIAL", "message": "<masked text>", ... }
5

Self-report the outcome

After the action actually happens (or is refused), log it — this closes the loop for Activity Log and Reports.

POST /v1/agent/activity
{
  "invoking_user_id": "<subscriber id>",
  "action": "device_diagnosis_completed",
  "outcome": "SERVED",
  "correlation_id": "<same id as step 3>"
}

05 Verification checklist

  • JioCare's agent appears in Agent Governance → Registered Agents, status active
  • A test decisions/check call with an unentitled subscriber returns DENY / IAM_SCOPE_EXCEEDED
  • After granting the entitlement, the same call with a consented subscriber returns ALLOW
  • A message containing an account number or OTP comes back PARTIAL from /guardrail_validate, masked
  • Activity Log shows paired rows (decision check + self-reported activity) sharing one correlation_id
